# CarePath AI v0.5 — Federated Health Platform Architecture

## North star

**One Patient. One Journey. One Trusted Health Record.**

CarePath is designed as a federated digital-health operating layer, not as a single database that replaces every provider system.

```text
Public / Private Source Systems
  EMR | GP | Lab | Pharmacy | Imaging | Scheduling | HIE
                    │
                    ▼
           CarePath Exchange
      identity + adapters + provenance
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
     OneRecord            CarePath Journey
  longitudinal view     referral / appointment /
                       transfer / follow-up
          │                   │
          └─────────┬─────────┘
                    ▼
        Ayanda + Professional Workspace
                    │
          ┌─────────┴──────────┐
          ▼                    ▼
 CarePath Command        Health Passport
 Population Health       Patient Portal
```

## Current v0.5 implementation

The hackathon runtime remains deterministic and adapter-backed. v0.5 adds working prototype APIs/UI for:

- Emergency Break Glass;
- Consent and Identity/MPI abstraction;
- Healthcare Professional Workspace;
- care plans and document/imaging metadata;
- CarePath Watch operational early warning;
- hierarchical Command Centre;
- Population Health Intelligence;
- mock source-system Exchange;
- FHIR R4-style Patient, ServiceRequest and Appointment resources;
- release/commit verification.

Existing v0.4 referral, appointment, capacity, ambulance, medication/vaccine, notification, facility, mobile and Health Passport functionality is preserved.

## Persistence architecture

Target production persistence is PostgreSQL with migration-capable typed repositories. The target schema is in:

`apps/api/prisma/schema.prisma`

The schema covers patient identity, consent, Break Glass, care plans, documents, tasks, integration events, access events and audit events.

**Runtime truth:** PostgreSQL is not yet wired to the hackathon runtime repositories. No production-persistence claim is permitted until a database has been provisioned, migrations have run and application repositories use it.

## Identity and MPI

CarePath does not invent a competing national health identifier.

The v0.5 prototype demonstrates:

- one CarePath synthetic identifier;
- multiple linked source-system identifiers;
- source-system provenance;
- deterministic synthetic linkage.

Production requires an approved authoritative identity/MPI service, verified demographic matching, duplicate review, governed merge/unmerge and legal/security review.

## Emergency access

Break Glass follows:

`Authenticated user → permitted emergency role → explicit reason → re-authentication → time-limited grant → minimum-necessary emergency summary → audit → compliance review`

The hackathon uses password re-authentication as a demonstrator. Production requires enterprise MFA/re-authentication, purpose-of-use controls and monitoring.

## Authorisation

Server-side controls remain authoritative.

- RBAC controls what a role may do.
- ABAC/purpose/context controls whether that action is appropriate for the patient, facility and care relationship.
- managers default to aggregated/de-identified operational views;
- auditors do not receive general clinical browsing rights;
- patient users see their own authorised information;
- clinical users require facility/care-scope or an active Break Glass grant.

## CarePath Watch

CarePath Watch currently uses transparent deterministic workflow rules, including:

- referral receiving delay > 24 hours;
- return feedback delay;
- missed appointment;
- zero synthetic bed capacity;
- critical ICU capacity constraints.

Each finding contains rule, evidence, owner and recommended administrative action. These are operational pathway signals, not diagnoses or clinical predictions.

## Command and population intelligence

The management hierarchy is:

**South Africa → Province → District → City → Facility → Service**

Country/province/district aggregation comes from v0.5 APIs. City/facility/service drill-down uses the same facility/service directory and synthetic capacity model.

Population Health Intelligence is aggregate/de-identified by design and must not expose patient identity unless an authorised clinical purpose separately permits it.

## Interoperability

CarePath Exchange currently exposes a mock FHIR R4-style facade for:

- CapabilityStatement;
- Patient;
- ServiceRequest;
- Appointment.

Mock source adapters represent clinic EMR, laboratory, pharmacy and specialist systems.

The architecture is intentionally extensible toward Observation, DiagnosticReport, Encounter, Condition, AllergyIntolerance, MedicationRequest/Dispense, DocumentReference, AuditEvent and Provenance.

No live source-system integration or national-profile certification is claimed.

## Security boundaries

The browser, uploaded content, voice transcripts and LLM are untrusted.

Consequential actions must flow through:

`User/Ayanda → validated tool request → authentication → RBAC/ABAC/purpose → workflow rules → confirmation where required → domain service → repository → audit`

No model may directly manipulate the database or decide clinical truth when source records conflict.

## Deployment verification

`GET /api/v05/release` reports:

- product/version;
- architecture label;
- runtime commit where supplied by the hosting platform;
- persistence mode;
- environment;
- synthetic-data flag.

A release must not be described as live until the hosting platform reports the intended commit and the deployed endpoint is verified.
